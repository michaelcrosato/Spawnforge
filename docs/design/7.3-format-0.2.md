# Design: format 0.2

Milestone 7.3 of [plan 2](../plan-2.md), worked at max effort. This document settles how a
blueprint says everything plan 2 adds, before any of it is built. A first draft went to an
independent adversarial review; this version answers it (see [Review](#review)).

## Goals and constraints

- **One coherent language.** Plan 2's additions read like plan 1's fields: the same words for
  placement (`on`, `at`, `angle`, `side`), the same pattern for module slots (a limb's `foot`), and
  the same merge rules. A model that learnt 0.1 should guess most of 0.2.
- **Short blueprints.** Every new field has a default, and defaults suit the role or body they
  sit on: `{ "id": "wing", "role": "wing" }` is a usable bat wing, and a dragon is a quadruped plus
  one wing entry.
- **Strict and explicit.** Unknown keys stay errors. Friendly forms are explicit and normalized in
  their own step. Likely guesses (`body.heads`, `hand`, `motion.fly`, `wing.feathered`) get hints
  or suggestions that name the real thing.
- **The core never names a module.** New behaviour arrives as modules (feet, membranes, parts,
  patterns, gaits, actions), with pack defaults and module fields carrying what the core needs.
- **No change of meaning.** No value a 0.1 blueprint can write changes meaning in plan 2. New
  behaviour comes as new fields, new modules and new defaults (0.x may change how a default
  creature looks). So every 0.1 blueprint is a 0.2 blueprint once its `format` is relabelled,
  and files saved as 0.2 before a later milestone stay correct after it. If a later milestone
  must change a meaning after all, it bumps the format and adds a step that runs on 0.2 files.
- **Validates before it is built.** The whole vocabulary validates now. What is not built yet
  validates, is skipped by compile, and is listed as not built with the milestone that builds it.

## Decisions

### 1. Several heads: a count on the neck

```json
"body": { "neck": { "count": 3, "length": 0.8 } }
```

- `count` (integer 1–9, default 1): necks, each carrying a head shaped like `body.head`, with the
  same jaw and the same parts. `spread` (0–170 degrees): the horizontal angle between the
  outermost necks. Left out, it is 25° per extra head (50° for three), so heads do not crowd at
  any count. The necks' roots spread across the front of the torso, not from one point.
- **Why a count and not a list.** Plan 2's scope has identical heads; different heads on one body
  are in "Later". A list (`body.heads: [{ … }]`) would invite per-head fields plan 2 cannot build
  and add merge rules and `[id=…]` paths. A count is one number to write; a later format can grow
  a list beside it.
- **Why on the neck.** One neck carries one head, and a hydra's count is a count of necks.
  `body.head.count` and `body.heads` get hints that point here.
- **Names.** The **main head** is the middle one (for an even count, the one just left of the
  middle). It keeps the plain names at every count: `neck`, `head`, `jaw`, `mouth`, and its bones
  keep today's names (`neck.0`, `head`, `jaw`), so random streams and goldens never move. The
  others are named outward from it, by side and rank: `head.L1`, `head.R1`, `head.L2`, … (and
  `neck.L1`, `jaw.L1`). The tokens start with a letter, so they never read as a bone index
  (`neck.2` is the third bone of the neck), and adding heads never renames existing ones.
- **Copies.** Parts on `head`, `jaw` or `neck` get one copy per head; a copy's id is the part's id
  plus the suffix of the instance it sits on, then its side: `horns.L` on the main head,
  `horns.L1.L` on `head.L1`. A part on a part follows the same rule, so ids never collide.
  `"on": "head.R1"` puts a part on that head only, as `"on": "foreleg.L"` does for limbs; naming
  an instance that does not exist is an error. Limbs are not copied: a limb `on` the neck sits
  on the main neck (name `neck.L1` for another).
- **Checks.** Validation warns `heads_overlap` when neighbouring heads would touch at rest
  (estimated from the neck length, spread, count and head size), with the spread or neck length
  that clears it.

### 2. Several and forked tails

```json
"body": { "tail": { "count": 2 } }
"body": { "tail": { "count": 2, "forkAt": 0.7 } }
```

- `count` (1–9, default 1), `spread` (0–170 degrees; left out, 20° per extra tail) and `forkAt`
  (0 to 0.95, default 0): with `forkAt` 0 the tails leave the torso separately (a two-tailed fox,
  a nine-tailed kitsune); with 0.7 one tail forks 70% of the way along. The name reads like
  `curlStart`. Each branch continues the tail's radius profile and curl from the fork.
- Names follow the heads: the main tail keeps `tail`, and the others are `tail.L1`, `tail.R1`, …
  Parts on `tail` get a copy per tail; on a forked tail, a part that sits wholly before the fork
  (a row ending at or before `forkAt`) is placed once, on the shared trunk.

### 3. New limb roles, each with its own fields and defaults

```json
{ "id": "wing", "role": "wing" }
{ "id": "pectoral", "role": "fin" }
{ "id": "arm", "role": "tentacle", "attach": { "at": 0.95, "angle": 150 }, "curl": 120 }
```

- Roles decide motion: legs carry the body, arms are free, wings fold at rest and beat in the
  air, fins steer and beat in water, tentacles are long spring chains that curl and reach. A
  role is a better switch than a module because the controller, analysis and defaults all branch
  on it, as plan 1 already does for `leg` and `arm`.
- **One schema per role.** `limbs[]` is a union keyed by `role` (a limb without one is a leg).
  Each role has its own fields, ranges and defaults, so the catalogue, the JSON Schema, `mutate`,
  `crossbreed` and the fuzz all see the right ones:

  | Role | Defaults | Own fields |
  | --- | --- | --- |
  | `leg` | `at` 0.5, `angle` 100, `length` 0.5, 3 segments, `foot.claw` | `splay`, `stance` |
  | `arm` | as a leg, hanging | `splay`, `lift` |
  | `wing` | `at` 0.2, `angle` 40, `length` 1.2, 3 segments, `membrane.bat`, no foot | `membrane` |
  | `fin` | `at` 0.25, `angle` 115, `length` 0.35, 2 segments, `membrane.fin`, no foot | `membrane` |
  | `tentacle` | `at` 0.9, `angle` 150, `length` 1.5, 10 segments (up to 16), no foot | `curl`, `curlStart` |

  Legs and arms keep 0.1's defaults exactly. A field on the wrong role is an unknown key with a
  hint (`curl` → "only tentacles curl").
- **Changing a role** replaces the inherited limb instead of merging into it (see decision 13),
  so turning a biped's arm into a wing does not drag along the arm's `lift`, segments and hand.
- **Attachment.** Wings, fins and tentacles attach to the torso, neck or tail, like legs and
  arms. Tentacles may also attach to the head (a face of tentacles).
- **Mirroring.** Every role mirrors with `side: "both"`, as now. A kraken's eight tentacles are
  four entries at different angles; `count` on a limb gets a hint saying so.

### 4. Membranes: a module slot on the limb, like `foot`

```json
{ "id": "wing", "role": "wing", "membrane": { "type": "membrane.feather" } }
{ "id": "wing", "role": "wing", "membrane": "membrane.insect" }
```

- Wings and fins carry a surface: a module in a new part slot, `membrane`, set through the limb's
  `membrane` field exactly as a foot is set through `foot`. Its parameters sit beside `type`;
  `null` means none. Like gaits and actions, `foot` and `membrane` also take the bare id as a
  string, which normalizes to `{ "type": … }`.
- Modules: `membrane.bat` (skin between finger bones, the body and the hind leg),
  `membrane.insect` (thin veined plates), `membrane.feather` (flight feathers on the wing bones),
  `membrane.case` (a beetle's hard wing case) and `membrane.fin` (rays with skin between them).
  One prefix keeps them together in the catalogue. Module-id suggestions also match on the last
  part of an id, so `wing.feathered` or `feathers` suggests `membrane.feather`.
- **Defaults by role**, from the pack: a wing gets `membrane.bat`, a fin `membrane.fin`. A
  flipper is a fin with `"membrane": null`: the limb itself is flat.
- **No limb ids in parameters.** Where a membrane meets another limb is a rule, not a
  reference: a bat membrane's trailing edge runs to the nearest same-side leg behind the wing,
  or to the body (`membrane.bat`'s `trailing`: `leg` or `body`), and a wing case covers the
  same-side wing behind it. Nothing breaks when `mutate` or `crossbreed` removes a limb.
- **Digits.** The membrane grows the wing's finger bones (the hook feet use for toes). A `foot`
  on a wing is the claw at the wrist (a bat's thumb), and grows no digits.

### 5. Feet by role; hands stay in `foot`

- Pack defaults become per role: legs and arms get `foot.claw`, wings, fins and tentacles none.
- Hands and pincers are foot-slot modules (`hand.grasp`, `hand.pincer`) set in `foot`:
  `"foot": "hand.grasp"`. A separate `hand` field would give each limb two ways to say one thing;
  `hand` as a key gets a hint to put it in `foot`.

### 6. Stance

`limbs[].stance` (legs only, optional): `plantigrade` (on the whole sole: bears, people),
`digitigrade` (on the toes: dogs, cats, birds) or `unguligrade` (on the hoof tips: horses). Left
out, the foot module suggests one (a new optional `stance` field on foot-slot modules); without a
suggestion the leg keeps today's pose. It is a limb field because it shapes the leg's rest pose
and planting, which the core owns.

### 7. Muscle and the S-neck

- `body.muscle` (0–1, default 0.5): how muscled the body is; 0 stays close to plan 1's tubes.
  `limbs[].muscle` (no default) overrides it per limb. The default is not 0, because phase 8
  exists to make the default creature look better; that is a new default, not a new meaning.
- `body.neck.curve` (-90 to 90 degrees, default 0): bends the neck into an S, forward at its base
  and back up below the head for positive values (a swan), the reverse for negative ones.

### 8. Heads: lips, tongue, brow

`body.head.lips` (0–1, default 0.3, the lips' thickness along the mouth cut), `body.head.tongue`
(`none`, `flat` or `forked`, default `flat`) and `body.head.brow` (0–1, default 0.2, a brow
ridge). They shape the skin and the inner mouth, which the core builds, so they are head fields;
hard pieces of the head (beaks, mandibles, antennae) are parts.

### 9. Coverings: an `area` slot

```json
{ "id": "quills", "type": "quills", "attach": { "on": "spine", "area": "back", "from": 0.3, "to": 0.9 } }
{ "id": "shell", "type": "shell" }
```

- A new part slot, `area`, scatters or conforms a part over an area of skin: `on` (a section,
  `spine` or a limb), `area` (`back`, `belly`, `sides` or `all`) and optionally `from` and `to`
  along it. How many pieces, and how close, are the module's parameters, since quills and scutes
  need different ranges. Each module's default anchor carries `area`, `from` and `to`, so
  `{ "type": "shell" }` alone sits on the back of the torso.
- The word is `area`, not `region`, because layers already use `region` with other values
  (`head`, `limbs`, …); each gets a hint pointing to the other.
- `area` in `attach` is accepted only for area-slot parts.
- Part slots for the new parts: `shell`, `armor.bands`, `quills` (area); `plates.row`, `sail`
  (row); `fin.dorsal`, `fin.tail`, `frill`, `hood`, `antenna` (surface); `beak`, `mandible`
  (mouth). A dorsal fin is one fin at `at` on the back; paired fins (pectoral, flippers) are fin
  limbs. blueprint.md says which is which, and suite B accepts either where both fit.

### 10. Hide and fur

- `skin.material` gains `hide` (thick, creased).
- Fur is an overlay, not a material: `skin.fur: { "length": 0.03, "density": 0.8, "region":
  ["torso", "limbs", "tail"] }` grows fur over any material, where its `region` says (a layer
  region or a list of them, default `all`). Present means furry; `"fur": null` removes an
  inherited coat. So a griffin has a furry body and a bare head, and a moth a fuzzy body with
  bare wings.

### 11. Swimming and flying: `motion.media`

```json
"motion": { "media": { "water": true } }
```

- `motion.media` says where the creature moves, as switches: `land`, `water`, `air`. It is an
  object, so it merges field by field over what the body suggests: `{ "water": true }` adds
  swimming and keeps walking and flying; `{ "air": false }` grounds a winged creature.
- What the body suggests: `land` when it has legs, or no legs and no fins or tentacles; `water`
  when it has fins or tentacles and no legs (a fish, a kraken); `air` when it has wings. Presets
  may set it too (`fish`: water only). Swimming is opt-in for walkers, since most game creatures
  never need it and it adds clips to every export.
- Gait modules declare the medium they serve (a new `medium` field, default `land`). Default
  gaits are those that suit the body in each medium it uses. An explicit `motion.gaits` list
  replaces the defaults only for the media its gaits serve: `["walk"]` on a dragon still flies.
- Presets stop listing gaits (each listed exactly its body's defaults), so new gaits such as
  `gallop` reach creatures that extend them.
- `air` with no wing is an error ("nothing to fly with: add a limb with role wing"), and so is a
  creature with every medium off. `motion.fly`, `motion.swim` and `motion.flying` get hints.

### 12. Stubs and what is not built

- Modules gain an optional `planned` field: the milestone that builds them (`"9.3"`). A planned
  module is the real module file (id, parameters, docs and example) without build hooks.
  Planned gaits and actions never join the defaults.
- Validation lists what is not built in its own field, `notBuilt`, beside `errors` and
  `warnings`: every planned module the blueprint uses, and every new core field it **writes**
  that the pipeline does not draw yet (`neck.count` above 1, a wing limb, a stance, fur, …).
  Defaults never count, so a blueprint that leaves `muscle` alone gets nothing. Each entry names
  the milestone and says to keep the feature. Keeping them out of `warnings` means an agent
  chasing a clean result is not tempted to delete its wings.
- Compile skips what it cannot build and reports the structural items (roles, counts, stance,
  fur, media) and planned modules in its warnings, so renders and `analyze` explain what is
  missing. A table in one core file maps fields to milestones, and each milestone deletes its
  rows.
- Body plans need no flag: `octopod` and `centaur` work now, while `wyvern` and `fish` validate
  and render without their wings and fins until 9.3.

### 13. Merging: a new type or role replaces

When an item or object sets `type` to something other than what it inherits (a foot, a
membrane, a layer, a part), or a limb sets `role` to another role, it replaces the inherited one
instead of merging into it. Otherwise `{ "id": "foreleg", "foot": { "type": "foot.hoof" } }` on a
quadruped would inherit the claw's `toes`, an error at a field the model never wrote. No preset
or saved blueprint relies on the old behaviour (the corpus test checks).

### 14. Format and migration

`format` becomes `spawnforge/0.2`. The 0.1 → 0.2 step only relabels, because nothing in 0.1
changes meaning. 8.3's head-relative tooth sizes arrive as new `teeth.row` parameters with
defaults; explicit 0.1 sizes keep meaning torso lengths.

### 15. Variation

Until 9.6 designs crossbreeding across counts, `count`, `forkAt`, `media` and `area` are fixed
genes: `mutate` and `crossbreed` never change them. Role-specific ranges come from each role's
schema.

## Alternatives considered

| Choice | Alternative | Why not |
| --- | --- | --- |
| Head count on the neck | `body.heads` list with per-head shapes | Different heads are out of scope; a list costs merge rules and paths |
| Main head keeps plain names | Heads numbered 1…N left to right | Numbers shift when the count changes, and `neck.2` already names a bone |
| Limb roles with a schema each | One limb schema with role checks in validation | Catalogue, genes and fuzz read the schema; role checks there would be invisible to them |
| `membrane` slot on the limb | Membrane parameters on the limb itself | Bat, insect, feathered and fin surfaces differ; modules keep the core out of it |
| `hand.*` in `foot` | A separate `hand` field | Two fields for one slot; the hint covers the guess |
| `media` object | A list (`["land", "water"]`), or booleans at `motion` level | A list replaces when patched and drops land; an object merges like the rest of 0.1 |
| Fur as an overlay with a region | `material: "fur"` | A griffin or a moth is furry in places; a material covers everything |
| `area` for coverings | `region` | Layers already use `region` with other values |
| No meaning changes; new fields instead | Extending the 0.1 → 0.2 step as milestones change meanings | Files saved as 0.2 in between would never be converted |

## Review

An independent reviewer read the first draft, plan 2, blueprint.md, the schema, validation,
merge and variation code, the presets and the agents' feedback from plan 1. Findings and what
changed:

| # | Finding | Answer |
| --- | --- | --- |
| 1 | Presets list `gaits`, and a gait list overrides media, so a winged quadruped would never fly and new gaits never reach preset creatures | Presets stop listing gaits; a gait list replaces defaults only within the media it covers (decision 11) |
| 2 | Limb defaults ignore the role: a bare wing is a half-length stub; turning an arm into a wing keeps the arm's fields | One schema and one set of defaults per role; a role change replaces the inherited limb (3, 13) |
| 3 | Merging keeps the old parameters when a slot's `type` changes (a hoof inherits the claw's `toes`) | A new `type` replaces instead of merging (13) |
| 4 | Role rules outside the schema are invisible to the catalogue, genes and fuzz; mutate could change head counts | A union keyed by role; `count`, `forkAt`, `media`, `area` fixed for variation until 9.6 (3, 15) |
| 5 | Changing tooth sizes in 8.3 by extending the 0.1 step misses files saved as 0.2 meanwhile | No meaning changes in plan 2: new parameters instead (constraints, 14); plan 2's 8.3 and its versioning rule are updated |
| 6 | Head numbering moves the main head, renumbers on count changes, collides with bone names, and part-on-part copies collide | Main head keeps plain names; others `L1`, `R1`…; copy ids carry the instance suffix; unknown instances are errors (1) |
| 7 | `media` as a list replaces on patch; the body-derived rule gets krakens and turtles wrong | An object that merges; tentacles count as swimmers; presets may set it (11) |
| 8 | `not_built` in warnings would tempt agents to delete features, and defaults would warn on every blueprint | A separate `notBuilt` list, computed on what is written (12) |
| 9 | Needs as a conjunction of fixed features cannot express `lash`, `pinch`, `display` or `hover` without naming modules; chains need drives other than springs | Modules provide capabilities; needs take alternatives; chains declare their drive and named poses (rig.md) |
| 10 | A membrane's trailing edge would need a limb id inside parameters | A rule: the nearest same-side leg behind, or the body (4) |
| 11 | Dorsal fins could be parts or limbs; a row part placed at one point spans the whole back | `fin.dorsal` is a surface part; paired fins are limbs; suite B accepts either (9) |
| 12 | `region` would mean two different things | Coverings use `area` (9) |
| 13 | Fur as a material covers everything (no griffin, moth or centaur) | Fur is an overlay with a region (10) |
| 14 | `membrane.feather` is hard to guess; strings would be shorter | Suggestions match the last part of an id; `foot` and `membrane` take a bare id (4) |
| 15 | `split: 0` reads backwards; parts on a shared trunk double up | `forkAt`; trunk parts placed once; branches continue the profile (2) |
| 16 | Heads crowd at a fixed spread; necks from one point | Spread grows with the count; roots spread across the chest; `heads_overlap` at validation (1) |
| 17 | Gaps: tentacle count and `curlStart`, foot versus membrane on wings, stance on non-legs, insect versus bat flight, eye-spots on wings, the six-gait limit, `limbs[].muscle` default | Hint for `count`, `curlStart` added; the membrane grows digits and a wing's foot is its wrist claw; stance on legs only; flight style is a capability; layer region `wings`; up to 12 gaits; `limbs[].muscle` has no default |

The reviewer also confirmed what to keep: counts rather than lists, roles for the new limbs, the
`membrane` slot mirroring `foot`, hands in `foot`, placement in `attach`, stubs with `planned`, an
additive format with one relabelling step, the rig with unchanged single-head names, gaits that
declare a medium, and `stance` on the limb.
